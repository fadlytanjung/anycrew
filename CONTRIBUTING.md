# Contributing

Thanks for helping. anycrew is small on purpose; the bar for a change is "a startup team would use
this on day one".

## Layout

| Path | What | Rule |
|---|---|---|
| `agents/*.md` | canonical agents | front matter `name`, `description`, `tier`, `model` (Claude alias, must match `models.json`), optional `tools`; body under ~12k chars |
| `skills/<name>/SKILL.md` | canonical skills | Agent Skills spec fields only; `metadata.anycrew-agent` names the agent; under 8 KB |
| `rules/*.md` | canonical rules | `trigger: always_on|model_decision|glob`; keep always-on rules short |
| `presets/*.json` | stack presets | commands, layout, globs, conventions |
| `models.json` | tier → model per tool | aliases over dated IDs |
| `templates/` | AGENTS.md and the docs skeleton | `{{placeholders}}` filled by the CLI |
| `plugins/claude/` | the Claude Code plugin, generated by `npm run build:claude` | never edit by hand; validation checks freshness |
| `lib/`, `bin/` | the Node CLI | zero dependencies, Node ≥ 18 |
| `src/anycrew/` | the Python CLI | zero dependencies, Python ≥ 3.9; must stay byte-identical to the Node CLI (`python3 tests/test_parity.py`) |
| `docs/` | the design docs | one question per page |
| `README.pypi.md`, `README.npm.md` | the PyPI and npm descriptions | Python-only / Node-only commands; keep in step with README.md (npm swaps it in during `prepack`) |

## Workflow

1. Open an issue or a draft PR describing the change in one paragraph.
2. `npm test` must pass (`scripts/validate.mjs` + `scripts/smoke.mjs`).
3. For a new assistant target: add it to `TOOLS`, `models.json`, `lib/generate.mjs`, the smoke test
   and `docs/04-tool-matrix.md` with its verification status.
4. For a new agent: add the file, reference it from at least one skill, add it to `docs/02-agents.md`.
5. Keep prose plain. No marketing language in agents, skills or docs.

## Releasing

Every release goes to npm and PyPI from one tag; `.github/workflows/release.yml` does the work.

1. `npm run bump -- X.Y.Z` sets the version in `package.json`, `pyproject.toml`, both plugin
   manifests and the marketplace file.
2. Add a `## X.Y.Z — YYYY-MM-DD` section to `CHANGELOG.md` (it becomes the GitHub Release notes).
3. Commit to `main`, then `git tag vX.Y.Z && git push origin vX.Y.Z`.
4. The workflow verifies the tag matches every version field, runs `npm test` and the parity test,
   publishes to whichever registry does not have that version yet, and creates the GitHub Release
   with the wheel and sdist attached. Re-running it is safe.

Both registries use trusted publishing (GitHub OIDC) configured against `release.yml`; no
long-lived tokens are stored. `npm run release:check` runs the same version check locally.
